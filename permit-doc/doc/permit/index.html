Permit: Signed Product Rights🔗ℹ

Turing Lambda <jirentianxiang1024@gmail.com>

 (require permit) package: permit

Permit is a framework-neutral protocol and Racket reference implementation for answering one product question: what may this person, organization, or installation use right now? Long-lived entitlements describe commercial rights, optional short-lived activation leases bind a right to an installation, and local first-run trials are their own convenience state. Everything is verified offline against an Ed25519 trust store that ships inside the application; issuance and rotation are online concerns that never change the verification protocol.

Permit is deliberately not anti-tamper DRM, and a permanently offline credential cannot learn about a revocation that happened elsewhere — see the threat model for the honest boundaries. The normative protocol lives in Protocol v1; this manual documents the Racket surface.

1 Trust stores🔗ℹ

Applications ship public keys only. A trust store is JSON application configuration, delivered through the application’s authenticated release path:

{
  "protocol": "permit-trust-store",
  "version": 1,
  "issuer": "com.example",
  "keys": {
    "license-2027": {
      "algorithm": "Ed25519",
      "public_key": "<Base64 SubjectPublicKeyInfo DER>",
      "status": "active",
      "purposes": ["entitlement", "trial", "trial-extension"],
      "not_before": "2027-01-01T00:00:00Z",
      "not_after": null
    }
  }
}

Key statuses are next (pre-distributed, must have not_before), active (normal issuance), retired (no new issuance, must have an not_after issuance cutoff — old credentials stay authentic), and revoked (every credential under the key fails). Each key declares the credential types it may sign; an activation-signing key therefore cannot mint a perpetual entitlement. The time windows constrain the credential’s authenticated issued_at, not the wall clock at verification — retiring a key never kills a perpetual entitlement.

2 Verifying credentials🔗ℹ

A credential is a small JSON envelope whose payload is base64 bytes signed exactly with Ed25519. Verification authenticates those bytes first and only then parses authorization claims — the verifier never re-serializes JSON, which removes canonicalization ambiguity across languages.

2.1 Verification failures🔗ℹ

A refusal is always an exception — fail-closed never returns a value — and carries a reason so a product can tell the customer what was wrong with a license file without matching message text. Time outcomes (expiry, not-yet-valid, installation mismatch, missing activation) are not refusals; they come back from credential-status as status reasons. See decision 0002.

struct

(struct exn:fail:permit exn:fail (reason))

  reason : symbol?
The parent of every Permit refusal, on the verifier and the issuer side. exn:fail:permit-reason is the one accessor for both.

struct

(struct exn:fail:permit:verify exn:fail:permit ())

Raised by verify-credential. Its reason is one of verify-failure-reasons. Messages keep the raise-arguments-error layout, so callers that matched message text keep working. A store that is not a trust-store? is a plain contract error, not a refusal.

value

verify-failure-reasons : (listof symbol?)

'(envelope key-unknown key-revoked signature schema issuer key-window key-purpose) in pipeline order — the wrapper could not be read or is not a Protocol v1 envelope; the key_id is not in the store; the key is revoked; the Ed25519 signature does not verify; the authenticated payload failed strict parsing or schema validation; the signed issuer differs from the store’s; issued_at falls outside the key’s issuance window; the key’s purposes do not include the credential type. Because the order is the order a conforming verifier checks in, the reason also tells you which guard refused.

4.2 Issuance failures🔗ℹ

struct

(struct exn:fail:permit:issue exn:fail:permit ())

Every refusal by issue-credential after its argument checks; read the reason with exn:fail:permit-reason (see Verification failures for the parent). The reason is one of issue-failure-reasons; the message keeps the raise-arguments-error layout, so callers that matched message text keep working. Argument-shape errors (a non-bytes? payload, a non-trust-store? store) remain ordinary contract errors.

value

issue-failure-reasons : (listof symbol?)

'(schema issuer key-unknown key-status key-window key-purpose key-mismatch) — the payload failed schema validation; its issuer differs from the trust store’s; the key-id is not in the store; the key is not "active"; issued_at falls outside the key’s issuance window; the key’s purposes do not include the credential type; the private key does not correspond to the store’s public key.

5 Host adapter🔗ℹ

 (require permit/adapter) package: permit

A host UI — SwiftUI, WinUI 3, GTK, or any other native shell — should not re-implement verification, status, and feature composition. permit/adapter evaluates one candidate credential, or no credential at all, into one small JSON-shaped result. The result is deliberately free of subject identity, claims, raw credential bytes, and trust material, and verification failures are a separate field from valid-but-unusable states, so a host can distinguish a forged or corrupt import from an expired license without parsing messages. The contract between hosts and this module is versioned; see the desktop adapter contract.

value

adapter-contract-version : exact-positive-integer?

The adapter contract version, currently 1.

6 Command line🔗ℹ

raco permit keygen --private k.der --public pub.der \

           --trust-store trust.json --key-id license-2027 \

           --issuer com.example

raco permit issue  --key k.der --key-id license-2027 \

           --trust-store trust.json --payload ent.json \

           --output customer.permit.json

raco permit sign   --key k.der --payload ent.json \

           --output customer.permit.json

raco permit verify --trust-store trust.json \

           --credential customer.permit.json

raco permit check  --trust-store trust.json \

           --credential customer.permit.json \

           --product example-app --edition pro

raco permit inspect --credential customer.permit.json

raco permit doctor

#

inspect is deliberately labelled unverified; never authorize a feature from inspected claims alone. sign is the deliberately low-level escape hatch that skips the issuer-side checks of issue. doctor prints the selected Ed25519 backend and per-provider availability as JSON.

(make-local-trial [#:duration-seconds duration-seconds 
  #:at at 
  #:id id]) 
 → local-trial?
  duration-seconds : exact-positive-integer? = (* 14 24 60 60)
  at : string? = (current-rfc3339)
  id : string? = (generate-local-trial-id)

procedure

(evaluate-local-trial trial 
  [#:at at 
  #:extensions extensions 
  #:issuer issuer 
  #:rollback-tolerance-seconds tolerance]) 
 → local-trial-evaluation?
  trial : local-trial?
  at : string? = (current-rfc3339)
  extensions : (listof verified-credential?) = '()
  issuer : (or/c string? #f) = #f
  tolerance : exact-nonnegative-integer? = 300
Evaluates the trial against the stored clock high-water mark and any verified trial-extension credentials. The result carries the updated state to persist.

A local trial is signed nowhere — it is convenience state with a random id and a last-seen clock high-water mark. That is nuisance resistance, not tamper resistance; a user controlling the machine can reset it.
