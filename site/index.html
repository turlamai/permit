缺失的产品层

付款，不等于权限。

支付事件只能证明钱已到账，账号只能证明用户身份。它们都不能给已安装的应用一个长期、可携带的答案：“这个用户现在可以运行什么？”

Permit 把答案变成签名制品。应用用已经信任的公钥在本地验证；Commerce 或其他明确的签发服务可以签发或刷新凭证，但授权判断不依赖服务此刻是否在线。

01

精确字节，没有歧义

Ed25519 对解码后的 payload 字节做精确签名。验证端绝不先解析 JSON、重新序列化，再验签。

02

权益不随网络消失

长期 entitlement 可以独立成立；只有当产品策略需要在线控制时，才叠加短期 activation lease。

03

商业策略不锁进平台

Permit 可以与 Rivet、Glaze、原生应用或其他运行时并列使用；应用框架不拥有商业授权策略。

RACKET 参考实现

从零到验证通过。

安装包、生成密钥对、签一个 payload，再只用公开信任库完成验证。

permit — shell
$ raco pkg install --auto \
  --name permit https://github.com/turlamai/permit.git

$ raco permit keygen \
  --private private-key.der \
  --public public-key.der \
  --trust-store trust-store.json \
  --key-id license-2026 \
  --issuer com.example

$ raco permit verify \
  --trust-store trust-store.json \
  --credential entitlement.permit.json

有意保留的边界

它是协议，不是账单公司。

Permit v0.1 不实现支付、账号、定价、税务、邮件、管理后台、托管计量或许可证服务器。家族内从支付到权益的流程由 Commerce 负责，并通过显式 issuer 边界签发凭证；它不进入验证核心。

选型判断

先完成一个可验证的结果。

需要签名且可离线验证的权益时，在应用旁组合 Permit。从 entitlement 开始；只有产品明确需要在线租约时才增加 activation。免费产品不需要授权子系统。

Racket 实现需要包声明的运行时与加密依赖。Protocol v1 已实现，但尚未宣布稳定 1.0 兼容承诺。独立验证器必须执行权威测试向量。

签发私钥留在签发端，客户端仅持公钥信任库。先验签，再判断产品、时间和功能政策。revision 替换客户端已收到的快照，不会立即撤销离线凭据。为永久权益保留备份和轮换路径，权益密钥与更新、发行者密钥分离。
